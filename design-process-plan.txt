DESIGN PROCESS PLAN
Portfolio site (evancmccaig/portfolio, theme: hugo-blog-awesome)
====================================================================

PURPOSE
--------
This is the shorthand format for specifying batches of content/design
changes in one shot instead of one prompt per edit. Write a list of
[Label] / [Content] pairs, hand it over, and it gets applied as one
pass: edited, built locally, verified, then committed and pushed
together.

This file is also the reference an AI agent (this one, or a different
one on a later session) reads FIRST before touching the site, so a
plan written today stays executable by whoever picks it up later.


FORMAT
------
Each instruction is one to three lines:

    [Label] Name of the element
    [Content] "The value to put there"

- Label   = which kind of element this is (see LEGEND below). A label
  is contextual, not a fixed 1:1 mapping — [Header] means something
  different next to "Title page" than it does next to "Projects
  Section". The Name line is what disambiguates it.
- Name    = which specific instance of that element.
- Content = the literal value — text in quotes, or a URL/file path
  for non-text elements (links, images).

Stack multiple instructions to batch unrelated changes together.
Order doesn't matter — they get grouped by which file they touch
before anything is edited.


LEGEND — label to site element
-------------------------------
| Label       | What it controls                             | Where it actually lives                              |
|-------------|-----------------------------------------------|--------------------------------------------------------|
| [Header]    | A top-level title — site identity or a new    | Site identity -> hugo.toml params.author.name/sitename |
|             | section's own heading                         | New section  -> content/<section>/_index.md title      |
| [Subheader] | The heading for one item inside a section     | content/<section>/<slug>.md title                       |
| [Sub-bio]   | A secondary descriptive line under a heading  | Homepage tagline -> hugo.toml params.author.description |
|             |                                                | Per-item bio -> body text in that item's .md file       |
| [Intro]     | Short line above the tagline (optional)       | hugo.toml -> params.author.intro                        |
| [Link]      | An embedded link/media element                | Raw HTML in the item's .md body (goldmark unsafe=true    |
|             |                                                | is enabled, so <iframe>/<div> embeds are allowed)        |
| [About]     | Body text of the About page                   | content/pages/about.md                                   |
| [Post]      | A blog post's title/body                      | content/posts/<slug>.md                                  |
| [Social]    | A social/contact link                         | hugo.toml -> [[params.socialIcons]]                       |
| [Avatar]    | Profile photo                                 | assets/avatar.jpg (file, not text)                        |
| [Menu]      | A nav bar entry                               | hugo.toml -> [[menu.main]]                                |

If a request uses a Name that doesn't map to anything that exists yet
on the site (e.g. "Projects Section" the first time it's mentioned),
that's a signal to BUILD the underlying structure first — new content
section, list/detail templates, menu entry — then apply the content
on top of it. See WORKFLOW step 2.


WORKFLOW — how to execute a batch (for any AI agent, not just this session)
------------------------------------------------------------------------------
1. PARSE. Read every [Label]/[Content] instruction, resolve each
   against the LEGEND, and write out the exact file + field each one
   will change. Flag anything genuinely ambiguous before touching
   files — but a Name that's simply new (see above) is not ambiguous,
   it's a build step.
2. BUILD STRUCTURE IF NEEDED. If an instruction targets a site element
   that doesn't exist yet (a new content section, a new nav item, a
   new embed pattern), create it before writing content into it:
     - New content section -> content/<section>/_index.md (list page)
       + content/<section>/<slug>.md (detail pages). Check whether the
       theme's existing layouts/list.html and layouts/single.html
       already render it acceptably before writing custom templates —
       this theme's generic templates cover most cases with zero new
       layout code.
     - New nav entry -> add a [[menu.main]] block in hugo.toml, with a
       `weight` placing it where it should sit in the nav order.
     - New embed/visual pattern -> prefer a small CSS addition in
       assets/sass/_custom.scss (this project-root file overrides the
       theme's own empty assets/sass/_custom.scss via Hugo's asset
       overlay — never edit the copy inside themes/hugo-blog-awesome/)
       over one-off inline styling, so the pattern is reusable next time.
3. APPLY CONTENT. Write the actual [Content] values into place.
4. BUILD LOCALLY. `hugo --gc --minify` from the repo root. Zero errors
   or warnings required before moving on.
5. VERIFY BY GREPPING OUTPUT. Don't trust "it compiled" — grep the
   actual built HTML under public/ for each changed value (title text,
   embed URL, CSS class actually present in the compiled stylesheet,
   etc.) so a silently-wrong template still gets caught.
6. RUN THE DOMAIN VERIFICATION CHECKLIST below.
7. COMMIT (one commit per batch, descriptive message) and PUSH — ask
   for confirmation before pushing unless told not to for that
   session.
8. RE-CHECK LIVE. After push, fetch the live URL and confirm the
   deploy picked up the change — a successful push is not the same as
   a successful deploy (Cloudflare can still fail the build; see the
   HUGO_VERSION incident logged below for what that looks like).


DOMAIN VERIFICATION CHECKLIST (run after every push)
-------------------------------------------------------
[ ] baseURL in hugo.toml matches the actual live URL
    (currently: https://portfolio-3i9.pages.dev/)
[ ] Cloudflare Pages "Deployments" tab shows the latest commit hash
    with a successful (not failed) build
[ ] HUGO_VERSION is pinned in Cloudflare Pages env vars (Production
    AND Preview) to a version that satisfies the theme's minimum
    (hugo-blog-awesome requires extended >= 0.160.0; this repo builds
    locally on 0.164.0)
[ ] Live page HTML actually contains the new content (fetch the live
    URL and grep for the changed string — don't trust "looks right in
    a screenshot", browser/CDN caching can show a stale page)
[ ] If the live page looks stale but the deployment succeeded: hard
    refresh / incognito test before concluding anything is broken —
    this is almost always cache, not a failed deploy
[ ] If a Retry/"force redeploy" of a previously-failed build still
    shows the identical error after fixing the underlying cause
    (e.g. an env var), don't trust it — Retry can re-run against the
    config snapshotted at original trigger time. Push a new commit
    (an empty one is fine) to force a genuinely fresh build.
